# team-collab

A four-file coordination workflow for small trusted groups building a shared repo,
where each person runs their own Claude Code instance.

## Why this exists

The bottleneck this solves is not code — it's coordination. When several people point
their own Claude Code at the same repo, three things go wrong: everyone waits on one
person to decide what to build, two agents silently edit the same files, and good ideas
evaporate in chat. Four plain markdown files in the repo fix all three, because every
Claude Code instance that opens the repo reads them automatically.

Keep the footprint tiny. Plain files, plain git, no server, no API keys, no build step.
Resist adding infrastructure — the value here is that a friend can clone the repo and be
productive in one minute with zero setup.

## The four files (in the target app repo)

| File | Purpose | Who writes it |
|---|---|---|
| `CLAUDE.md` | Auto-loaded workflow brief for any Claude Code opening the repo | Written once by `init` |
| `IDEAS.md` | Append-only idea backlog | Anyone, anytime |
| `TASKS.md` | Who is actively building what | Whoever claims work |
| `PRIORITIES.md` | Ranked build order + conflicts + questions | Generated by `triage` |
| `dashboard.html` | Static readable snapshot of the above | Generated by `dashboard` |

`IDEAS.md` is append-only on purpose: two people adding ideas at the bottom of a file
rarely conflict in git, so contributors don't need to understand branching to participate.

## Subcommands

Determine which the user wants from their phrasing. If genuinely ambiguous, ask — but
prefer inferring: "what should we build next" means `triage`, "set this repo up" means
`init`, "refresh the page" means `dashboard`.

### `init`

Scaffold the workflow into the current working directory (the target app repo).

1. Check which of the four files already exist. **Never overwrite an existing file** —
   this command must be safe to rerun on a repo that's already set up, because people
   will run it again out of uncertainty and losing their ideas backlog would be a
   serious, unrecoverable failure.
2. For each missing file, copy the matching template from `assets/` in this skill
   directory, substituting `{{PROJECT_NAME}}` with the repo's directory name and
   `{{DATE}}` with today's date.
   - `assets/CLAUDE.md.template` → `CLAUDE.md`
   - `assets/IDEAS.md.template` → `IDEAS.md`
   - `assets/TASKS.md.template` → `TASKS.md`
   - `assets/PRIORITIES.md.template` → `PRIORITIES.md`
   - If `CLAUDE.md` already exists with unrelated content, don't clobber it. Append the
     contents of the template under a `## Team collaboration workflow` heading instead,
     so existing project instructions survive.
3. Generate the initial dashboard (see `dashboard`).
4. Report which files were created and which were skipped, then tell the user the next
   step: commit and push, and add collaborators on GitHub.

### `triage`

Turn the raw idea backlog into a decision. Read `IDEAS.md` (and `TASKS.md`, so you don't
rank something that's already being built), then **rewrite** `PRIORITIES.md` entirely.

This is the judgment-heavy part of the skill, and it's why a human reading the backlog
is not enough — you're looking for the things that are hard to see when ideas arrive one
at a time over weeks:

- **Ranked build order.** Lead with what unlocks the most downstream work or delivers
  user-visible value soonest. Note dependencies explicitly ("needs #3 first") rather than
  silently ordering around them, so the reasoning survives disagreement.
- **Duplicates and near-duplicates.** Name both ideas and propose which phrasing to keep.
  Two people describing the same feature differently is the most common failure in an
  append-only backlog.
- **Contradictions.** Ideas that can't both be true (offline-first vs realtime-sync,
  minimal-UI vs feature-rich dashboard). Surface the tension and what the group must
  decide — don't quietly pick one, because that decision belongs to the people.
- **Suggested rejects.** One line of reasoning each. Frame as a recommendation, not a
  verdict; the proposer should be able to push back. Being able to say "not this" is
  what keeps the backlog usable, but a triage pass that silently deletes people's ideas
  will make them stop contributing.
- **Clarifying questions.** For ideas too vague to act on, address the question to the
  proposer by name. This is how an async group resolves ambiguity without a meeting.

Preserve the proposer's name against each idea throughout. Attribution is what makes
people keep contributing.

Use `assets/PRIORITIES.md.template` for the section structure. Add a "last triaged"
date at the top. After writing, regenerate the dashboard, then summarize the top three
items and any contradiction you found — that's the part the user actually needs to see.

### `dashboard`

Regenerate `dashboard.html` from the current contents of the three markdown files.

Run the bundled script from the repo root:

```bash
python3 "$SKILL_DIR/scripts/build_dashboard.py"
```

It reads `IDEAS.md`, `TASKS.md`, and `PRIORITIES.md` from the current directory and
writes a single self-contained `dashboard.html` — inline CSS, no JavaScript, no external
requests. Pass `--output` to write elsewhere, `--title` to override the heading.

The page is deliberately a static snapshot, not a live view. A live page would need a
hosted API key and a backend, which is a large jump in cost, complexity, and risk for a
group that is already all running Claude Code locally. Instead the page tells readers how
to refresh it themselves. Don't add fetch calls, polling, or a backend to this page
unless the user explicitly asks for that tradeoff.

### `update`

Pull the latest version of this skill from the canonical meta-repo and reinstall it.
This is explicit-only — never run it as a side effect of the other subcommands, because
a tool that silently rewrites itself mid-task is impossible to reason about.

```bash
bash "$SKILL_DIR/scripts/update_skill.sh"
```

The script pulls the meta-repo (skipping cleanly if it has no remote yet) and copies
`skills/team-collab/` over the installed copy, reporting what changed. Set
`TEAM_COLLAB_REPO` to override the meta-repo location — friends who clone the meta-repo
elsewhere will need this.

## Working in a repo that already uses this workflow

When you're just doing normal development in a repo that has these files (rather than
running a subcommand), the repo's own `CLAUDE.md` governs: check `TASKS.md` before
starting, claim what you pick up, and append new ideas rather than acting on them
unilaterally. The point of claiming is that another person's Claude Code may be editing
the same files right now, and git will not warn you until it's too late.
