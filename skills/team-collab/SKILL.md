# team-collab

A file-based coordination workflow for small trusted groups building a shared repo, where
each person runs their own Claude Code instance and they all need to act like one.

## Why this exists

The bottleneck this solves is not code — it's coordination. When several people point
their own Claude Code at the same repo, three things go wrong: everyone waits on one
person to decide what to build, two agents silently edit the same files, and good ideas
evaporate in chat. A handful of plain markdown files in the repo fix all three, because
every Claude Code instance that opens the repo reads them automatically.

Keep the footprint tiny. Plain files, plain git, no server, no API keys, no build step.
Resist adding infrastructure — the value here is that a friend can clone the repo and be
productive in one minute with zero setup.

## The files (in the target app repo)

| File | Purpose | Who writes it |
|---|---|---|
| `CLAUDE.md` | Auto-loaded workflow brief for any Claude Code opening the repo | Written once by `init` |
| `IDEAS.md` | Append-only idea backlog | Anyone, anytime |
| `CONTEXT.md` | Shared understanding: decisions, gotchas, how things work | Anyone, as they learn |
| `JOURNAL.md` | Running conversation: reasoning, open debates, what settled them | Anyone, as they discuss |
| `TASKS.md` | Who is actively building what | Whoever claims work |
| `PRIORITIES.md` | Ranked build order + conflicts + questions | Generated by `triage` |
| `dashboard.html` | Static readable snapshot of the above | Generated by `dashboard` |

`IDEAS.md` is append-only on purpose: two people adding ideas at the bottom of a file
rarely conflict in git, so contributors don't need to understand branching to participate.

## Subcommands

Determine which the user wants from their phrasing. If genuinely ambiguous, ask — but
prefer inferring: "what should we build next" means `triage`, "set this repo up" means
`init`, "refresh the page" means `dashboard`.

### `init`

Scaffold the workflow into the current working directory (the target app repo).

1. Check which of these files already exist. **Never overwrite an existing file** —
   this command must be safe to rerun on a repo that's already set up, because people
   will run it again out of uncertainty and losing their ideas backlog would be a
   serious, unrecoverable failure.
2. For each missing file, copy the matching template from `assets/` in this skill
   directory, substituting `{{PROJECT_NAME}}` with the repo's directory name and
   `{{DATE}}` with today's date.
   - `assets/CLAUDE.md.template` → `CLAUDE.md`
   - `assets/IDEAS.md.template` → `IDEAS.md`
   - `assets/CONTEXT.md.template` → `CONTEXT.md`
   - `assets/JOURNAL.md.template` → `JOURNAL.md`
   - `assets/TASKS.md.template` → `TASKS.md`
   - `assets/PRIORITIES.md.template` → `PRIORITIES.md`
   - `assets/gitattributes.template` → `.gitattributes` (append to it if one exists).
     Don't skip this one — it sets `merge=union` on the append-only files. Without it,
     two people adding an idea at the same moment collide at the end of the file and
     git's rebase silently keeps only one of them. That's a verified failure, not a
     theoretical one, and losing someone's contribution is the fastest way to make
     people stop contributing.
   - If `CLAUDE.md` already exists with unrelated content, don't clobber it. Append the
     contents of the template under a `## Team collaboration workflow` heading instead,
     so existing project instructions survive.
3. Generate the initial dashboard (see `dashboard`).
4. Report which files were created and which were skipped, then tell the user the next
   step: commit and push, and add collaborators on GitHub.

### `triage`

Turn the raw idea backlog into a decision. Read `IDEAS.md` (and `TASKS.md`, so you don't
rank something that's already being built), then **rewrite** `PRIORITIES.md` entirely.

This is the judgment-heavy part of the skill, and it's why a human reading the backlog
is not enough — you're looking for the things that are hard to see when ideas arrive one
at a time over weeks:

- **Ranked build order.** Lead with what unlocks the most downstream work or delivers
  user-visible value soonest. Note dependencies explicitly ("needs #3 first") rather than
  silently ordering around them, so the reasoning survives disagreement.
- **Duplicates and near-duplicates.** Name both ideas and propose which phrasing to keep.
  Two people describing the same feature differently is the most common failure in an
  append-only backlog.
- **Contradictions.** Ideas that can't both be true (offline-first vs realtime-sync,
  minimal-UI vs feature-rich dashboard). Surface the tension and what the group must
  decide — don't quietly pick one, because that decision belongs to the people.
- **Suggested rejects.** One line of reasoning each. Frame as a recommendation, not a
  verdict; the proposer should be able to push back. Being able to say "not this" is
  what keeps the backlog usable, but a triage pass that silently deletes people's ideas
  will make them stop contributing.
- **Clarifying questions.** For ideas too vague to act on, address the question to the
  proposer by name. This is how an async group resolves ambiguity without a meeting.

Preserve the proposer's name against each idea throughout. Attribution is what makes
people keep contributing.

**Rejections and deprioritizations must outlive the file they're written in.**
`PRIORITIES.md` is rewritten from scratch every triage, so reasoning left only there
disappears on the next run — and then the same idea gets re-proposed, re-debated, and
re-rejected forever. That loop is one of the most demoralizing things that can happen to
a group backlog.

So whenever you reject an idea or push one well down the order for a substantive reason,
also **append it to the Decisions section of `CONTEXT.md`**: what was proposed, who
proposed it, what was decided, and the reasoning. Then, before ranking anything, read
`CONTEXT.md` first — if an idea matches something already settled there, say so and keep
the existing decision rather than quietly reversing it. Reversals should be deliberate:
if new information genuinely changes the picture, note what changed.

Skip this for the trivial cases (an obvious duplicate, or something already built) — the
decisions log is only useful while it stays readable.

Use `assets/PRIORITIES.md.template` for the section structure. Add a "last triaged"
date at the top. After writing, regenerate the dashboard, then summarize the top three
items and any contradiction you found — that's the part the user actually needs to see.

### `dashboard`

Regenerate `dashboard.html` from the current contents of the three markdown files.

Run the bundled script from the repo root:

```bash
python3 "$SKILL_DIR/scripts/build_dashboard.py"
```

It reads `IDEAS.md`, `TASKS.md`, and `PRIORITIES.md` from the current directory and
writes a single self-contained `dashboard.html` — inline CSS, no JavaScript, no external
requests. Pass `--output` to write elsewhere, `--title` to override the heading.

The page is deliberately a static snapshot, not a live view. A live page would need a
hosted API key and a backend, which is a large jump in cost, complexity, and risk for a
group that is already all running Claude Code locally. Instead the page tells readers how
to refresh it themselves. Don't add fetch calls, polling, or a backend to this page
unless the user explicitly asks for that tradeoff.

### Quick commands (what people actually type)

The dashboard tells readers to type these bare words into their own Claude Code. Nobody
should have to remember file names or markdown format to take part — that friction is
what stops people contributing. Treat these as first-class:

| They type | You do |
|---|---|
| `idea: <anything>` / "add idea" | Append to `IDEAS.md` in template format, filling in their name and today's date. Ask for the name only if you can't infer it from git config. Then regenerate the dashboard. |
| `triage` / "what's next" | Run the `triage` flow below. |
| `claim <thing>` / "claim task" | Add a row to the In-progress table of `TASKS.md` with their name, today's date, and a suggested branch name. Create the branch if the repo is clean. Regenerate the dashboard. |
| `done` | Move their in-progress row to the Done section of `TASKS.md` with today's date. Regenerate the dashboard. |
| `refresh` / "refresh dashboard" | Run `sync` (if the repo is on GitHub), then the `dashboard` flow below. |
| `sync` | Pull idea issues from GitHub into `IDEAS.md` — see below. |
| `status` | Summarize in chat: what's in progress and by whom, top three priorities, open threads awaiting their view, anything blocked. Don't write files. |
| `catch me up` / "what did I miss" | Pull, then summarize what changed in `JOURNAL.md`, `CONTEXT.md`, and `TASKS.md` since their last activity (use `git log` to find it). Don't write files. |

After any command that changes a markdown file, regenerate `dashboard.html` and offer to
commit and push — an update nobody pushes is invisible to the rest of the group, which is
the most common way this workflow quietly stops working. Commit only when they agree.

Infer the person's name from `git config user.name` rather than asking every time.

## The goal: one shared mind, several people

The target experience is a single agent that has worked on the project continuously and
happens to talk to several people — not several agents each holding a fraction. What
prevents that is simple: each person's chat history is private, so reasoning that happened
in one person's conversation is invisible to everyone else.

That's why capture is not bookkeeping. It's the mechanism. `IDEAS.md` and `TASKS.md` carry
state, `CONTEXT.md` carries conclusions, and `JOURNAL.md` carries the reasoning and the
arguments still in flight — which is the part that usually evaporates, and the part
someone needs in order to disagree intelligently rather than re-tread old ground.

**Start every session by catching up.** Pull, read `JOURNAL.md`, `CONTEXT.md`, and
`TASKS.md`, then open by telling the person what changed since they were last here and
flagging any open thread that wants their view. A person coming back after two days
shouldn't have to ask what they missed — and an agent that skips this will confidently
contradict a decision made yesterday.

## Capture as you go (this is the part that makes it work)

The workflow fails in a specific, predictable way: people discuss something good in chat,
nobody writes it down, and a week later the repo has no memory of it. So don't wait to be
asked — when something durable surfaces during ordinary conversation, record it.

Record without being asked when, in the course of any conversation:

- **A feature or improvement is floated** ("it'd be nice if…", "we should probably…") →
  append to `IDEAS.md` under the speaker's name. Even if it's rejected in the same breath,
  log it with the reasoning; the group re-proposes forgotten ideas endlessly otherwise.
- **You start real work on something** → claim it in `TASKS.md` before the first edit, not
  after. Someone else's Claude Code may be starting the same thing right now.
- **You finish something** → move it to Done.
- **A decision gets made** ("let's use Postgres, not SQLite") → append to `IDEAS.md` as a
  decision entry with the reasoning. A decision nobody recorded gets relitigated.
- **A blocker appears** → mark the task `blocked` and say what it's waiting on.

Two judgment calls matter here. First, don't log every passing thought — noise makes the
backlog unreadable, which is the same failure as an empty one. Log things someone would
want to find later. Second, mention what you recorded in one short line rather than
silently editing files; people need to trust the record matches what they meant, and
correcting a wrong entry is easy only if they know it exists.

## Committing and pushing

After changing any coordination file, publish it. An update nobody else can see is the
same as no update — that's the failure mode this whole workflow exists to prevent.

```bash
bash "$SKILL_DIR/scripts/publish.sh" "coordination: <what changed>"
```

The script commits **only** `IDEAS.md`, `TASKS.md`, `PRIORITIES.md`, and `dashboard.html`,
then pushes — rebasing and retrying when someone else pushed first, which happens
constantly when several people's agents are writing markdown. On a genuine conflict it
stops and tells the user rather than force-pushing, because their idea is worth more than
a clean history. Regenerate the dashboard *before* publishing so the page matches the files.

Code is deliberately different. Never auto-push code to shared `main`: work on the branch
named in the task claim, and let the person decide when it's ready to merge. Half-finished
work landing on everyone else's `main` is exactly what the branch discipline prevents.

If the user says to stop auto-publishing, respect it for the session and just commit
locally — some people want to review before their team sees anything.

### `sync` — GitHub Issues as the discussion layer

Markdown files are a good backlog but a poor conversation: you can't reply to one line of
a file, and two people editing it at once conflict. GitHub Issues already solves that —
threading, reactions as lightweight voting, notifications, and it works from a phone. So
ideas can arrive from two places, and `sync` folds the issue side into the file side.

Requires the `gh` CLI. Check `gh auth status` first; if it's missing or the repo has no
GitHub remote, say so plainly and carry on with the file-only workflow rather than failing.

```bash
gh issue list --label idea --state all --limit 200 \
  --json number,title,body,author,createdAt,state,comments,reactionGroups
```

For each issue not already in `IDEAS.md`, append an entry in the normal template format,
with `- **Issue:** #<number>` added so the file links back to the discussion. Match on
issue number, not title, so re-running is safe and edited titles don't create duplicates.

When triaging, weigh the discussion, not just the title: 👍 reactions signal support, and a
long comment thread usually means either strong interest or an unresolved disagreement —
check which, because they point in opposite directions. Closed issues mean the group
already decided; list them under rejects with that as the reason rather than re-ranking
them.

If the user asks to post an idea *for discussion* rather than just log it, create the issue
with `gh issue create --label idea` and let `sync` bring it back. Confirm before creating —
an issue notifies everyone, so it's a message to the group, not a local edit.

### `update`

Pull the latest version of this skill from the canonical meta-repo and reinstall it.
This is explicit-only — never run it as a side effect of the other subcommands, because
a tool that silently rewrites itself mid-task is impossible to reason about.

```bash
bash "$SKILL_DIR/scripts/update_skill.sh"
```

The script pulls the meta-repo (skipping cleanly if it has no remote yet) and copies
`skills/team-collab/` over the installed copy, reporting what changed. Set
`TEAM_COLLAB_REPO` to override the meta-repo location — friends who clone the meta-repo
elsewhere will need this.

## Working in a repo that already uses this workflow

When you're just doing normal development in a repo that has these files (rather than
running a subcommand), the repo's own `CLAUDE.md` governs: check `TASKS.md` before
starting, claim what you pick up, and append new ideas rather than acting on them
unilaterally. The point of claiming is that another person's Claude Code may be editing
the same files right now, and git will not warn you until it's too late.
